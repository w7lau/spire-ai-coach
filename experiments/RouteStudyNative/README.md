# Frozen-route study

This independent launcher compares complete native routes from different frozen combat roots. It references an already accepted product DLL; it does not modify the product or install an experimental policy.

Build with `dotnet build experiments/RouteStudyNative/RouteStudyNative.csproj -c Release -p:NativeCoachDll=<accepted-dll> -p:GameDir=<installed-game>`. Run from the repository root with `dotnet <launcher> <owned-root> <game> <cases.json>`. The output root must be inside this checkout's ignored `work` directory and contain `.route-study-owner`. Put the matching product manifest beside `cases.json`.

The private configuration contains `ProductSha256`, `Workers`, `MaxNodes`, `BudgetSeconds`, `Repeats`, `ModDirectories`, and `Cases` (`Name`, `Request`, optional per-case `ModDirectories`). Optional `Algorithms` lists `MonteCarlo`/`TurnFrontier`. `Modes` defaults to `current`; `absolute-priority` disables only the existing resource-efficiency ordering hint, while `fresh-continuations` disables only existing winning-route guidance. These are experimental ablations, not proposed defaults. Alternate order on odd repeats; report warmup and scheduling limitations.

`loss-round-refinement` is a separate experimental parent-scheduler patch. After an accepted incumbent, it stably reorders the existing winner-refinement queue by observed gross HP loss in the affected round. It leaves potion-using incumbents on the original ordering, preserves the exact task multiset, and does not change other scheduler lanes, native effects, pruning, bounds or result ranking. `loss_round_reorders` proves whether the hypothesis was exercised. The patch and Harmony dependency are local to the console; game workers receive only the accepted product DLL. Such a result is an experiment with a modified parent, not validation of an unchanged end-to-end product or a shipped fix.

Each unseeded run clears the retained frontier and removes answer seeds and verification candidates. It preserves the captured native root, complete history, Mod state, potion permission, goals, action and round limits. Only the explicitly declared study budget, algorithm or hint switch varies. Every final candidate, including losses, receives ordinary independent native replay. Winning results additionally require complete execution checkpoints, actual native victory without escape, and valid proof when stopping on minimum loss. Runtime failures remain failures and are excluded from quality/speed comparisons.

The follow-up decision study optionally accepts a per-case `InitialPlanPath` containing an observed native action prefix. These are explicitly seeded counterfactuals, normally one complete rollout each. They measure the consequence of an early choice under the unchanged rollout policy, not discovery speed or guaranteed optimal continuation. Both the launcher and `analyze_decisions.py` check that the returned route actually starts with the supplied native prefix, including state, instance, target and supplied choice identities. Unspecified choices remain native proposals. A positive result from one such route does not prove every continuation from its sibling is worse.

For a controlled continuation study, a case may additionally provide `SoftContinuationPath`, only with `MonteCarlo`. The prefix plus tail are passed through the product's existing native proposal resolver; old tail states are not replay assertions. The declared prefix is checked against actual returned actions independently. Tail actions or choices that are no longer legal can be skipped or replaced, so inspect actual actions before attributing effects to a proposed change. These seeded, continuation-guided studies are explicitly labeled and cannot establish normal search discovery or a universal best continuation. Keep paired unchanged-tail controls.

`DecisionStudy` runs only in the parent launcher and records private claimed tasks, partial focus messages and improving complete candidates. Focus messages contain only the producer's next decision and observed goal-loss decisions; they are not complete rollout traces. The private native result retains the full final route and timing trace.

- `fresh-guided-tail`: keep branch ordering, but clear a claimed guided task's soft continuation and prevent the worker's secondary fallback to an old route. This differs from disabling winning-route guidance entirely.
- `goal-before-proof`: while the selected incumbent lacks complete finite card goals, defer dedicated proof-focus proposals. Keep observations, certificate calculation and final proof checks intact. This hypothesis is not a shipped policy.
- `goal-continuation`: when an already claimed prefix has tried a selected goal card and reached a later round, request a full Preparation rollout with fresh continuation. This uses the action identity only as a scheduling hint; actual goal credit still comes from native events. The branch order, legal histories, pruning and proof rules remain unchanged.
- `retained-goal-seed`: compare completed native goal counts first, then retain a winning exploration seed with more unspent root finisher copies immediately before its final operation. The parent remembers that observation when the product compacts a guided incumbent. This ablation changes proposal seeds only, not final result ranking or native goal credit. A result from this mode is not evidence that the unchanged product can find the same route; retest a product implementation in `current` mode.

Use `python experiments/RouteStudyNative/analyze_decisions.py <run> ... --output <sanitized-json>` for these follow-up studies. Place the matching configuration at `<run>.json`. The exporter checks seeded prefixes and marks interrupted batches explicitly, including only individually finished results. Do not combine a partial batch with a completed batch without disclosing it. Parent instrumentation has overhead, so compare modes within the same instrumented batch.

Preparation is reported separately. Incumbent curves are callback-observation times, not exact first-discovery timestamps. Keep raw requests, routes, full traces, installed game/Mod binaries, absolute paths and identities ignored. Publish only sanitized aggregates. A frozen synthetic or historical case, fewer workers, or smaller budget cannot establish default-setting or general-game performance. Repeated wins and a zero lower bound do not establish global optimality.

Export the allowlisted metrics with `python experiments/RouteStudyNative/summarize.py <completed-run> ... --product-version <version> --output <sanitized-json>`. The exporter rejects incomplete runs and mixed product hashes, retains failures as categories and omits paths, native identities, Mod lists, raw captures, full routes and detailed traces. Review that output before sharing.

`summarize_followup.py` also exports per-batch product hashes for explicit before/after comparisons, gross HP lost, HP gained, native health targets and runtime-error counts. Its first-win-at-final-HP fields identify the earliest complete winning outcome at the final HP, not an executable return time, goal certificate or independent verification. Compare equal completed-attempt budgets separately from wall-clock budgets. A higher final HP with revival is not a reduction in gross damage. Runtime-error/partial runs remain visible but are not valid quality comparisons.

The follow-up export includes the mode, selected goal HP-loss threshold, actual plays/kills and finite finisher completion. Distinguish a selected finisher from a selected play goal: a zero play-goal count does not prove the finisher card was never played. Inspect the private native action sequence for that question. The October 16 finisher study uses one 169-HP frozen root with two goal settings; its round-10 player log is not a second replayed root. See `docs/validation.md` for rejected candidates and the remaining incomplete finisher goal.
