# 0.6.3 存档占用修复（2026-10-02）

## 实际故障

玩家通过旧精英房，经过休息点进入下一精英房，重新继续却返回旧精英房。真实游戏日志连续三次记录 `GodotFileIo.RenameFile` 失败：`current_run.save.tmp` 和 `current_run.save` 均存在，临时文件无法替换正式存档。之前日志中的 0.5.0 和 0.6.1 均出现这一故障；现场用 0.6.2 再次打开游戏并运行后台计算时也捕获到了占用。

正式存档及备份都停在旧房间，检查时没有可恢复的新进度临时文件。日志还记录了启动时清理遗留 `.tmp`。未修改或推断重建玩家存档；原始日志与存档只保存在本地私有工作目录，不纳入仓库。

## 根因证据

1. 主游戏未运行时，打开真实存档的替换权限探针成功。
2. 主游戏和四个后台模拟进程运行时，相同探针得到 Windows 错误 32（共享冲突）。
3. 只读枚举游戏进程句柄，发现 `worker-2` 持有指向真实用户 `current_run.save` 的可继承只读句柄。此时主游戏已不持有该文件句柄。
4. 停止这四个已确认归属的后台模拟进程，保留主游戏运行，再次检查即成功。
5. 后台游戏日志的 userdata 指向各自独立目录，Steam 未初始化。故障来自 OS 句柄继承，独立目录并不能隔离已打开的文件句柄。

RitsuLib 在异常栈中只包装并等待保存 Task。该堆栈位置不足以归责于它；现场句柄证据已定位到本项目后台进程。

## 修复

后台启动由普通 `Process.Start` 改为 Windows `CreateProcessW`，显式设置 `bInheritHandles=false`。保留独立 APPDATA/LOCALAPPDATA、禁用 Steam、隐藏窗口、静音及原有启动参数。通过挂起创建、绑定 Process 句柄后恢复线程，避免短生命周期进程退出造成 PID 获取竞态；失败时只终止本次刚创建的进程并释放句柄。

不通过修改主游戏句柄属性、强行关闭其句柄、删除存档、绕过保存失败或延长重试掩盖问题。API 语义参见 [Microsoft CreateProcessW 文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)。

## 定向验证

Windows 双进程回归使用合成文件：父进程创建可继承、禁止替换的读取句柄，然后启动子进程并关闭父句柄。旧 `Process.Start` 对照下替换失败；新启动器下子进程仍存活时替换成功。还检查中文/空格路径、空参数、引号和反斜杠参数、独立 APPDATA/LOCALAPPDATA、工作目录、退出码、缺失可执行文件失败路径。1/1 通过，未运行全量测试。

0.6.3 编译零警告零错误。已在主游戏退出后安装，安装 DLL 与构建 DLL SHA256 相同：`83bbe68e287222dcfd6fdeb76d7937551cd602541a8638e868929e6a3b9f8c90`。

随后运行独立 NativeProbe 工作区的 `--optimization` 短原生集成：冷启动与复用搜索均完成，原生回放校验通过，搜索期间测试宿主指纹未改变，后续 4 步方案续用通过，游戏日志 `[ERROR]` 为 0。该测试使用独立合成战斗，不加载玩家真实存档，完成后测试进程全部退出。

本修复不恢复此前未保存的过关进度。主游戏真实过关后的保存与重进结果需要后续运行确认。
