# 模拟性能与下一步方向（0.7.3）

当前是原生游戏执行器上的结算反馈搜索：每条路线恢复同一个当前操作点，连续执行合法卡牌、目标、选择和结束回合，直到胜负或预算边界。操作树根据实际终局反馈安排探索；通用路线调整再提出补牌、删牌、换牌、牌序及选牌目标变化，继续执行完整后续战斗。它不是穷举，也不是在纯内存结构上瞬间 Fork 的模拟器。

旧真实记录中，决策约占三秒并行累计时间，动作执行、恢复及复核远高于它。固定 35 步获胜路线的配对测试也显示，原生动作等待与复核占主导。因此先优化这些路径，比修改打分公式或降低搜索预算更直接。具体数字与样本边界以 validation.md 的最终证据为准，多个并发 lane 的累计时间不能当作墙钟等待时间。

## 已实现的底层改动

- 隔离模拟跳过 CreatureCmd 的角色动画入口；保留所有卡牌、怪物逻辑、原生同步及 Mod 钩子。
- 只在后台绕过生成选牌页面的 350ms 防误点延迟，仍通过原生处理器确认选择并记录历史；实际游戏执行保留输入保护。
- 后台搜索范围内设置 TimeScale=8、MaxFps=240，加速剩余原生动画/帧等待；退出搜索恢复原值。
- 所有进程先返回未复核的候选，父进程按终局目标选出拟采用路线，只对它作独立原生重放。失败就弃用该候选，其他候选也必须独立通过同样检查才能发布。未复核结果不能进入显示续用或真实执行。
- 保留资源和后台进程，避免每次点击重新启动或每条路线重复加载公共资源。首次恢复准备单列，搜索预算保持 60 秒，实际显示的总耗时仍包含准备、搜索及复核。

这些改动仍需场景，不能称作“已经完全纯代码”。受真实墙钟、动画回调或未序列化私有状态影响的 Mod 尚无全面兼容证明。每步原生状态及最终结算核对是必要检查，并不能证明所有私有字段相同。

## 同时钟时间轴

父进程和隔离模拟使用同一主机的高精度单调时钟。真实界面入口从点击前读取快照开始计时，包含等待提前准备的队列；已经在点击前完成的预热不计入这次等待。准备阶段分为资源/配置、创建进程和引擎/Mod 就绪。每次恢复再分清理、解码、建立运行状态、资产准备、创建场景、重放已经完成的历史和根状态核对。搜索记录逐步决策、动作、原生队列与稳定等待，最终复核单独标记。

2026-10-03 的冻结真实战斗采用原 4 路、45 秒/32 路线预算：请求到结果 90.007 秒。最后完成搜索的一路准备 32.521 秒、首次恢复 6.550 秒；首次恢复于请求后 39.269 秒完成，搜索过程到 84.413 秒，最后复核在 84.554–89.756 秒。其他进程的准备和搜索相互重叠，因此不能把它们串成 300 多秒的时间轴。这个实验入口不是用户实际按钮，尚不含人工窗口交互验收。

四路搜索阶段合计 206.283 秒，其中动作 155.254 秒（约 75.3%）、恢复起点 41.717 秒（约 20.2%）、决策 5.720 秒（约 2.8%）。恢复中的场景建立合计 27.065 秒、角色与地图资源准备 7.810 秒；解码和状态建立合计约 4.696 秒。本次根本没有已经出牌的历史前缀，因此历史重放耗时接近零，不能泛化到战斗中途。一次正常请求只有最终采用路线需要独立复核，耗时约 5.2 秒。

从这些数据可优先研究：去除更多纯表现节点/回调、避免每条路线重建场景、建立可完整恢复的分叉检查点。其次研究进度序列化；单纯优化树的选择函数不会消除主要等待。原生卡牌效果、RNG、Mod 钩子、胜利回血和状态验证必须完成，但它们目前依赖的固定帧等待和场景构建不是理论上的不可缩减成本。时间轴测量的是墙钟时间，仍不足以把每段拆成 CPU 工作、线程调度、GC 与空等；不能将全部动作耗时直接认定为动画或全部“必须等待”。

每个进程最多记录 16384 段，父进程合并最多 65536 段，超过上限只省略诊断细节、不会缩短搜索预算。嵌套动作/队列等待不能重复相加。本次 7022 段记录没有截断；可展开准备、搜索和最终复核，并在相同时刻查看各路活动。时钟和记录不参与任何卡牌决策、RNG 或状态指纹。

## 大幅度提速需要什么

最大的潜在改进是从纯数据检查点分叉后继续计算，避免恢复战前状态、重放共同前缀及创建 UI 节点。但游戏当前保存格式和同步指纹不包含任意 Mod 的完整私有/静态状态，不能拿可见状态哈希假装完整检查点。

可拆成两个有明确边界的实现方向：

1. 使用游戏原生非交互及选择接口，逐个确认 UI 依赖可以移除，保留同步、重放历史、原生伤害/回血/抽牌/消耗及钩子。每个变化与正常执行比较完整逐步状态、历史和结算；遇到依赖节点的 Mod 必须保留原生路径。原生测试选择器本身可能绕过 choice ID 或同步记录，不能直接开一个 TestMode 开关就当作实机等价。
2. 建立可复制的纯战斗状态与机制执行器，支持按当前状态直接 Fork、复用公共前缀、转置表和安全的支配剪枝。基础效果可共享通用接口，但未登记的 Mod 机制需明确适配或退回原生执行。它能避免大量引擎开销，却无法免费获得任意 Mod 兼容性。

[CombatSolver 的搜索说明](https://github.com/Torch1230/CombatSolver/blob/main/docs/strategy/search-logic-explained-20260912.md)区分完整终局排序、中途保路、消耗选牌以及用药/不用药代表；[第三方适配说明](https://github.com/Torch1230/CombatSolver/blob/main/docs/THIRD_PARTY_ADAPTERS.md)表明纯状态模拟仍有显式的扩展边界。这里参考搜索组织与边界，未复制其效果镜像或源码。

即使一个状态真的只需一微秒，一亿个状态也需一百秒；卡牌游戏的节点通常还包含抽牌顺序、RNG、选择组合、敌人状态和钩子，并非一次简单整数比较。几亿状态能否快速计算应通过具体吞吐实验判断，不能由“无画面”直接推断。

## 搜索质量与可证明的目标

完整获胜、战后净损失 0 且不耗药，已经达到这两个成本轴的下界；这不证明回合最短、奖励最大或所有其他状态最优。没有达到该下界时，只能说是预算内已找到并复核的最好方案，不能把进度条或搜过若干条路线当作全局最优证明。

压缩的原生效果是将可转化的手牌状态牌变成燃料，燃料可回能并消耗；它并非直接消耗所有诅咒。后续消耗触发抽牌、格挡及其他 Mod 效果由实际执行兑现。搜索必须比较这些动作后完整战斗的结局，而不是把当前无攻击意图时的格挡或暂时零伤害等同于没有作用。
